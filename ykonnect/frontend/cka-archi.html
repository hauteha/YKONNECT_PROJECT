Module 1 — Architecture & Composants Kubernetes

Comprendre le plan de contrôle, les nœuds workers et la communication entre composants.

CKA Architecture · ~2h · 12% examen

Vue d'ensemble d'un cluster Kubernetes

Un cluster Kubernetes est composé de deux types de nœuds :

  • Control Plane (Master) — cerveau du cluster, prend les décisions d'orchestration
  • Worker Nodes — exécutent les charges de travail (conteneurs)

Composants du Control Plane

kube-apiserver

Point d'entrée unique pour toutes les opérations. Expose l'API REST Kubernetes. Authentifie, autorise et valide chaque requête. Tous les autres composants communiquent exclusivement via l'API Server.

# Vérifier l'API server kubectl get --raw /healthz kubectl cluster-info

etcd

Base de données clé-valeur distribuée (Raft consensus). Stocke tout l'état du cluster : objets, configurations, secrets. Un seul etcd en dev, 3 ou 5 nœuds en production (quorum).

# Lister les clés etcd (depuis le control plane) ETCDCTL_API=3 etcdctl get / --prefix --keys-only \ --cacert=/etc/kubernetes/pki/etcd/ca.crt \ --cert=/etc/kubernetes/pki/etcd/server.crt \ --key=/etc/kubernetes/pki/etcd/server.key

kube-scheduler

Surveille les Pods sans nœud assigné (Pending) et choisit le meilleur nœud selon :

  • Les ressources disponibles (CPU, mémoire)
  • Les contraintes (nodeSelector, affinity, taints/tolerations)
  • Les policies de spreading

kube-controller-manager

Exécute les boucles de contrôle (reconciliation loops). Chaque contrôleur surveille un état cible et agit pour l'atteindre :

  • ReplicationController — maintient le nombre de réplicas voulu
  • NodeController — détecte les nœuds défaillants
  • EndpointsController — peuple les Endpoints des Services
  • ServiceAccountController — crée les comptes de service par défaut

Composants des Worker Nodes

kubelet

Agent qui tourne sur chaque nœud. Reçoit les PodSpecs depuis l'API Server et s'assure que les conteneurs décrits tournent correctement. Communique avec le container runtime via CRI.

# Vérifier le statut kubelet sudo systemctl status kubelet sudo journalctl -u kubelet -f

kube-proxy

Maintient les règles réseau (iptables ou IPVS) pour implémenter les Services Kubernetes. Assure le routage des paquets vers les bons Pods.

Container Runtime

Responsable de l'exécution des conteneurs. Kubernetes utilise l'interface CRI (Container Runtime Interface). Runtimes supportés :

  • containerd — le plus utilisé en production
  • CRI-O — runtime léger pour Kubernetes
  • Docker — via dockershim (déprécié depuis K8s 1.24)
# Vérifier le runtime utilisé kubectl get node -o wide # Colonne CONTAINER-RUNTIME : containerd://1.7.x

Communication dans le cluster

# Flux d'une commande kubectl apply : kubectl apply → API Server → etcd (état stocké) → Scheduler (assigne nœud) → kubelet (crée le Pod) → container runtime (démarre le conteneur)

Commandes essentielles CKA

# Voir les composants du control plane kubectl get pods -n kube-system # Informations sur le cluster kubectl cluster-info kubectl cluster-info dump | head -50 # Voir les nœuds et leurs rôles kubectl get nodes -o wide # Décrire un nœud (capacité, conditions, pods) kubectl describe node <nom-noeud> # Vérifier la version de l'API Server kubectl version

Questions type examen CKA

Q : Quel composant est responsable de l'assignation d'un Pod à un nœud ?
R : kube-scheduler
Q : Où est stocké l'état du cluster Kubernetes ?
R : Dans etcd
Q : Quel composant tourne sur chaque worker node et gère les Pods ?
R : kubelet
