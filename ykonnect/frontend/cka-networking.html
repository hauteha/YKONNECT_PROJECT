Module 3 — Services & Networking

Services, Ingress, NetworkPolicy, DNS interne et modèle réseau Kubernetes.

CKA Networking · ~2h · 20% examen

Modèle réseau Kubernetes

Kubernetes impose un modèle réseau simple :

  • Chaque Pod reçoit une IP unique dans le cluster
  • Les Pods communiquent entre eux sans NAT
  • Les nœuds communiquent avec tous les Pods sans NAT
  • L'IP visible d'un Pod est la même depuis l'intérieur et l'extérieur du Pod

Ce modèle est implémenté par un plugin CNI (Container Network Interface) : Calico, Flannel, Cilium, Weave…

Services

Un Service expose un ensemble de Pods via une IP virtuelle stable (ClusterIP). Les Pods sélectionnés via labels.

ClusterIP (défaut)

IP virtuelle accessible uniquement depuis l'intérieur du cluster.

apiVersion: v1 kind: Service metadata: name: webapp-svc spec: selector: app: webapp # Cible les Pods avec ce label ports: - protocol: TCP port: 80 # Port du Service targetPort: 8080 # Port du conteneur type: ClusterIP

NodePort

Expose le Service sur un port de chaque nœud (30000-32767). Accessible de l'extérieur via <NodeIP>:<NodePort>.

spec: type: NodePort ports: - port: 80 targetPort: 8080 nodePort: 30080 # Optionnel, assigné auto sinon

LoadBalancer

Provisionne un load balancer externe (cloud provider). En on-prem : utiliser MetalLB.

spec: type: LoadBalancer ports: - port: 80 targetPort: 8080

ExternalName

Mappe un Service vers un FQDN externe (DNS CNAME).

spec: type: ExternalName externalName: api.externe.com

DNS interne — CoreDNS

CoreDNS résout les noms de services dans le cluster. Format DNS :

# Depuis un Pod, accéder à un Service : <service>.<namespace>.svc.cluster.local # Exemples : webapp-svc.default.svc.cluster.local postgres.database.svc.cluster.local # Raccourci (même namespace) : webapp-svc # Tester la résolution DNS depuis un Pod kubectl run test --image=busybox --rm -it -- nslookup webapp-svc

Ingress

Expose des Services HTTP/HTTPS avec routage basé sur host/path. Nécessite un Ingress Controller (nginx-ingress, Traefik, HAProxy…).

apiVersion: networking.k8s.io/v1 kind: Ingress metadata: name: webapp-ingress annotations: nginx.ingress.kubernetes.io/rewrite-target: / spec: rules: - host: app.mondomaine.fr http: paths: - path: /api pathType: Prefix backend: service: name: api-svc port: number: 80 - path: / pathType: Prefix backend: service: name: frontend-svc port: number: 80 tls: - hosts: - app.mondomaine.fr secretName: tls-secret

NetworkPolicy

Contrôle le trafic réseau entre Pods. Par défaut, tous les Pods peuvent communiquer librement. Les NetworkPolicy sont additivement permissives.

# Interdire tout le trafic entrant vers les Pods du namespace "production" apiVersion: networking.k8s.io/v1 kind: NetworkPolicy metadata: name: deny-all-ingress namespace: production spec: podSelector: {} # Cible tous les Pods policyTypes: - Ingress # Pas de règle Ingress = tout bloquer
# Autoriser uniquement le trafic du namespace "monitoring" apiVersion: networking.k8s.io/v1 kind: NetworkPolicy metadata: name: allow-monitoring namespace: production spec: podSelector: matchLabels: app: webapp policyTypes: - Ingress ingress: - from: - namespaceSelector: matchLabels: name: monitoring ports: - protocol: TCP port: 8080

Commandes réseau clés

# Créer un Service impératif kubectl expose deployment webapp --port=80 --target-port=8080 --type=ClusterIP # Voir les Endpoints d'un Service kubectl get endpoints webapp-svc # Debugger le réseau avec un Pod temporaire kubectl run debug --image=nicolaka/netshoot --rm -it -- bash # Vérifier les NetworkPolicy kubectl get networkpolicy -n production # Voir la configuration CoreDNS kubectl get configmap coredns -n kube-system -o yaml
💡 À l'examen : savoir créer un Service rapidement avec kubectl expose et débugger avec un Pod busybox ou nicolaka/netshoot.
⚠️ Les NetworkPolicy ne fonctionnent que si le CNI les supporte (Calico, Cilium oui — Flannel non par défaut).
